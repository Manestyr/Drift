# Simulation boundaries and extension contracts

## Current implementation

`ShipPhysics` owns the authoritative physical state. Only `_integrate_forces` applies thrust/torque and performs the explicitly requested debug reset. `FlightCommand` contains bounded local translation/rotation requests and main throttle. `PilotInput` is a replaceable adapter. `main.gd` samples it once per physics tick before the physics-server step; the body consumes the latest complete command. State observations have an integer `tick` and `state_sampled(tick)` signal. Signal observers must not mutate simulation state during integration. No render delta enters the flight integrator.

Crew uses a separate SubViewport/World3D as a local simulation space. No colliders are duplicated into the global flight simulation. Its CharacterBody, deck collisions and gravity are local. Rendering switches between the local viewport and actual ship cameras; this deliberately avoids moving-platform CharacterBody velocity artifacts. Ship identity is supplied by composition rather than an autoload. For a future Zero-G mode, replace only the local movement/inertial-force policy: local velocity and position remain explicit, artificial gravity can be zero, and a frame adapter can supply local effective acceleration and angular terms. An EVA crossing must explicitly convert pose and velocity, including ship linear velocity and omega cross offset; do not simply reparent the current CharacterBody.

`CrewStation.enter() -> bool`, `leave()`, `occupied` and `occupancy_changed(bool)` provide exclusive occupancy for this single-player prototype. Interaction rules (range, E) live in the composition layer, not in the station. Human/AI providers can later both emit `FlightCommand`. The station currently holds no network identity or authority rules. A later host must validate operator identity, station ownership and command limits itself.

Physics and input are separate modules; world/UI construction remains in one small composition script. Refactor geometry into scenes when assets or a second ship warrant it, rather than adding framework layers now.

## Planned contracts, deliberately not implemented

These describe integration boundaries, not shipped systems or empty scaffolding:

| Module | Inputs | Output / ownership |
|---|---|---|
| Sensors | host tick, sensor world pose, candidate physical states | timestamped contact observations with stable entity IDs; no direct weapon mutation |
| Missiles | validated station command, launcher pose/velocity, target/contact ID | host-owned physical entity, launch event; guidance consumes observations |
| Drones | operator intent, carrier frame and observations | bounded flight commands for their own body, deployment/recovery events |
| Damage | collision/hit event including tick, IDs, contact pose, impulse/energy | damage result event; explicit game-rule consumer changes component state |
| Replay events | validated commands, spawn/reset/station/damage events, tick IDs | ordered event log plus periodic full snapshots; rendering consumes playback state |

A future command envelope should contain `{tick, entity_id, station_id, operator_id, sequence, command}`. A host resolves one command per entity/tick with explicit stale/missing-input rules. Replay events should include `{tick, sequence, type, entity_id, payload}`; snapshots must include body pose, velocities, mass/configuration, station state and random generator state. Do not assume cross-machine floating-point physics is deterministic: record snapshots and correct playback as needed. Input polling or HUD text is not a replay source.

The future physiology consumer should receive local proper-acceleration vector, angular state and fixed dt, and integrate exposure by direction and duration. Today's exponential visual filter lives entirely in presentation and must not become a damage rule.

## Milestone 0.1.1: local operator input

`PlayerInput` is a scene-owned adapter, shared by this operator's crew controller and pilot input adapter. It reads **Input Map actions only**; `ShipPhysics` still consumes only `FlightCommand` and has no knowledge of controllers. `movement()`, `camera_rate()` (radians/second) and `sample_flight(command)` expose contextual intent. Human/AI/network adapters can eventually implement those boundaries without modifying the body. `PilotInput.sample(command, source)` preserves its keyboard-only fallback for existing callers.

Stick actions have zero Input Map deadzone, followed by one radial filter (default 0.15, output remapped continuously to 0–1). A 1e-6 boundary tolerance accounts for Vector2 float precision. Trigger actions have a separate 0.05 Input Map deadzone. Left stick drives local movement on foot and pitch/yaw when seated; right stick drives local look or lateral/vertical RCS. Sensitivity affects look angular rate and pilot pitch/yaw request, not physical thruster ratings or trigger strength. Inversion affects only controller look/pitch. LT uses the existing backward RCS channel: adding a rear main engine is not part of this milestone.

The last meaningful key/button/stick/mouse event selects the active source; inactive-source held axes are not mixed into commands. Sub-deadzone stick motion, releases, neutral triggers and tiny mouse motion do not steal the source. The last active pad's disconnect returns to keyboard input. Device events affect presentation/adapter selection, never simulation directly. HUD uses both Xbox/PlayStation labels because driver-reported brand names are unreliable.

`PauseMenu` and the input adapter run while the scene tree is paused; the physical bodies, crew and game composition stop. Start/Options or P toggles pause, B/Circle or Escape closes it. Controls use normal Godot focus navigation, with explicit cyclic vertical neighbors. Confirm events in the menu cannot reach the paused station handler. Closing saves `InputSettings` to `user://input_settings.cfg`; no project files are modified. Reset is also accessible here, so no keyboard is needed for development recovery.

Current actions accept **any one mapped local controller** (`device = -1`), and Godot's Input singleton merges those events. `active_device` supports disconnect handling; it is not multiplayer device isolation. Before adding multiple local operators, provide per-device action snapshots to separate adapter instances and bind each operator to a station/host identity. Do not share merged local input between network players. Hardware remapping, trigger calibration and controller glyph art are outside this milestone.

## Milestone 0.1.2: physical flight computer and input contexts

This section supersedes the earlier keyboard mapping and raw-torque rating. The single authoritative integrator remains `ShipPhysics._integrate_forces`; neither adapters nor UI write physical velocities/orientation. `FlightCommand` now carries held local brake-axis masks, full-brake and roll-brake requests. Discrete stabilize/hold/reference choices change controller policy; a future host/replay implementation must timestamp these policy events as well as the command snapshots.

`FlightComputer` is a scene-owned RefCounted value controller with no Input API, world lookup or RigidBody reference. `solve` receives body basis, world linear/angular velocity, actual principal inertia, mass and actuator budgets. It returns local force/torque fields consumed by the integrator. Rotation/translation RCS are separate actuator groups. Physics damping stays zero. A standalone body starts with assistance off; game composition enables rate stabilization as the playable default.

Control laws (SI units):

- Linear braking: `F_auto = -m * selected_local(v_world - v_reference) / 0.8 s`. Saturate to available RCS norm. No velocity assignment, exact-zero cutoff or fictitious drag.
- Rate stabilization: `alpha = -omega_local / 0.5 s` on uncommanded axes.
- Attitude hold: shortest-arc normalized quaternion error; `alpha = 1.6 * rotation_error_local - 2.529822 * omega_local` (critically damped unsaturated PD). No integrator/windup. Multiply by actual principal inertia, then limit torque in normalized actuator space.
- Local roll braking uses the rate law only on Z. Manual rotation releases the captured attitude target; manual actuation masks automation on each affected axis.

A manual normalized vector gets its requested budget first. Orthogonal automation gets the remaining `sqrt(1 - |manual|²)` fraction, so the combined actuator request stays within one norm and does not silently weaken manual input. Main thrust masks automatic longitudinal braking. HUD reports remaining translation-RCS capacity; ETA explicitly assumes free RCS and is not a promise during manual input/contact. Progress restarts when brake axes or inertial reference change. ETA integrates saturated first-order deceleration to a 0.05 m/s tolerance; no hard velocity snap is used at that threshold.

The explicit uniform-box inertia is aligned with body principal axes. The integrator observes `1 / state.inverse_inertia`, rather than assuming the renderer's shape establishes the inertia. Torque ratings correspond to 0.4 rad/s² on each isolated axis. About yaw, 5.38 MN·m is consistent with opposed ~149 kN jets at 18 m lever arms; roll uses much smaller torque appropriate to its smaller inertia. This is a reference mass/actuator model, not a detailed thruster layout or shared propellant system.

`PlayerInput` now owns a bounded, self-centering virtual mouse stick; relative events update **intent** only, and fixed-tick sampling consumes it. Main composition routes mouse to crew look, flight intent or exterior orbit by context. Logical `controls_captured` is the gameplay authority; `Input.mouse_mode` implements the OS presentation of that state (and cannot report real capture in headless mode). Context/pause/device switches clear buffered intent. Ctrl consumes regular keyboard flight commands, including mouse/main thrust, before axis-brake selection. The controller's explicit RS-click camera modifier temporarily consumes translation/trigger actions; release requires their neutral state before flight re-arms. Normal controller axes have not been reassigned.

Computer settings use a separate pause submenu so existing resume/deadzone/sensitivity/invert/reset/quit focus order remains stable. D-pad layouts and held-brake axis selection persist in `InputSettings`. A selected inertial frame is a constant world velocity: arena rest or a virtual -20 m/s world-Z convoy. Neither is a rotating ship frame or a tracking autopilot. Selected local component axes follow the body orientation; full braking is invariant under rotation except actuator/manual budget limits.

`TestArena` owns static scenery/collisions (layer 1); the local crew world uses its existing layer 2. All 72 asteroids use shared low-poly sphere mesh/material, matching static spherical collision shapes. The wreck uses 14 static boxes. References/grid have no collisions and the main launch corridor is deliberately clear. `ExteriorOrbit` changes only a Camera3D pose, with bounded pitch/radius; it never applies ship transforms. No new global singleton or framework was added.

## Milestone 0.1.3: observer-only cockpit instruments

`ShipPhysics`, `FlightComputer` and `FlightCommand` are byte-for-byte unchanged from 0.1.2. The existing `state_sampled` signal is the only simulation integration point: composition obtains the physics direct state inside the callback and constructs a new typed `ShipTelemetry` snapshot. This avoids mixing a freshly sampled input command with last tick's actuation or relying on a render-frame body-property cache. All three instruments receive the same snapshot/tick and retain no ship or computer reference. Snapshot fields are read-only by convention. Mutating them never mutates the simulation.

The snapshot includes orientation, world/local and selected-frame-relative velocity, world/local applied acceleration, local angular rate, main fraction, normalized actual RCS force/torque, inferred limited automatic contribution, computer modes, brake axes/budget/progress/ETA and frame name. Automatic contribution is actual combined RCS output minus that tick's manual normalized request, not the unlimited PD demand. It is computed only for display; it is never fed back into control. Acceleration retains the existing thrust/proper-acceleration definition and excludes collision impulses and crew angular-load effects.

`CockpitInstruments` owns three 512×448 viewports and mounts their textures on QuadMeshes with individual beveled-looking box frames, pedestals and a shared console/canopy support. The meshes are ship children, never children of the screen-space CanvasLayer. The local interior gets a second physical mesh mounting of the **same three textures**, not three more render targets. These decorative frames do not add mass or colliders; the existing ship and interior collision geometry remain unchanged. Only the obsolete visual cockpit sill was removed after it obstructed the lower readouts.

`NavigationInstrument` renders a real independent World3D: three torus rings, axis labels, cylinder/cone arrows and an orthographic camera. It uses a fixed oblique view for legible depth. Its reusable `InstrumentFace` draws titles/readouts **after** the background so numeric values are not overpainted. Forward length is one; velocity/acceleration lengths scale to 20 m/s and 2 m/s², clamp to 0.15–1 for nonzero visibility, and hide below 1e-5. Numeric values are never clamped. World-axis mode changes the coordinate basis only; the selected inertial reference velocity is subtracted consistently in both modes. Zero acceleration hides the green arrow while drift remains orange.

`PropulsionInstrument` and `ComputerInstrument` are separate Control components drawing within their viewports, using the shared color/font convention and typed snapshot. Signed bar zero is centered, orange is actual actuation, green is the limited computer contribution. Display-only normalization and unit conversion are the only arithmetic here. There are no control laws, physical writes or Input calls in instrument renderers. The small callback-based readout extension of `InstrumentFace` only composes drawing, not simulation behavior.

The normal pilot camera position, direction and flight controls are retained. Console planes sit at approximately `(−1.13/0/+1.13, 0.98, −20.05)` in ship coordinates, lean 12° upward toward the pilot, and angle outer displays 10° inward. Physical faces are 1.05×0.92 m. A 1280×720 projection test checks every corner and minimum projected size. The 24-pixel main text lands around 16 screen pixels high. Rendered virtual-display captures additionally check actual texture orientation, frame occlusion, draw order and readable numbers. No physics or mouse rotation changes are involved.

Main composition keeps the prior technical HUD text but sets its visibility off by default and toggles it together with the debug menu on F3. Routine CanvasLayer output is limited to a nearby-station prompt and the existing g-vignette. N and a controller-accessible pause-menu checkbox select navigation axes. Mouse flight sensitivity is an input setting (default 1), scales only virtual mouse-stick motion, and is persisted alongside the existing settings. New menu controls are appended so the established controller focus order remains compatible.

Future station displays can consume `ShipTelemetry` directly or introduce station-specific snapshots without a global state singleton. Network/replay adapters could serialize snapshots later; no transport, replay or combat subsystem was added.

## Milestone 0.1.4: commanded drift, directional budgets and retrograde

This section supersedes the old 240 kN translation rating and uniform spherical force allocator. No permanent lateral-assist flag exists. `FlightCommand.drift_cancel` is a held input, cleared with every command snapshot and on station/pause context clear. Each `FlightComputer.solve` recomputes `(basis.inverse() * (v_world - v_reference)).xy`, adds only X/Y to the explicitly requested brake mask, then masks manually commanded axes. `drift_active` describes the command, not an inferred velocity/turn condition. Releasing it removes that force request on the next fixed tick; no release smoothing or residual controller integrator is present. Other explicitly held brake commands remain independent.

Translation budgets are signed: X/Y ±1.2 MN, reverse +Z 1.44 MN, forward manoeuvre -Z 1.2 MN, main -Z 2.4 MN. The body's aggregate forward ceiling is 2.4 MN, so actual main thrust reduces the remaining negative-Z manoeuvre allocation. `ShipPhysics` exposes all four ratings as configuration. Each axis request is normalized against the capacity for its own sign. Manual force is allocated first; automation gets the remaining normalized ellipsoid radius. Zero-capacity directions do not spend imaginary manual budget. The allocator cannot produce force from a disabled direction. Rotation keeps the previous independent torque limits and inertia. Main and manoeuvre force are transformed to world axes and applied only through `PhysicsDirectBodyState3D.apply_central_force`; torque still uses `apply_torque`.

Full-brake and drift ETA now integrate saturated first-order braking using the force available in the actual desired signed direction, not a uniform scalar. Missing capacity/manual takeover yields an unavailable ETA. Changed attitude and manual thrust can change the estimate; the target remains zero, while 0.05 m/s is only the display/test tolerance and never a velocity clamp. No fuel or individual thruster-location/mass-flow model was introduced; shared translation and independent rotation ellipsoids are explicit gameplay approximations.

Retrograde is a command-driven state machine inside the fixed-tick controller: requested → orienting → settling → aligned; cancellation and low-speed inhibition have explicit statuses. `request_retrograde()` only requests policy; it never changes the body or supplies a main-engine command. In solve, relative velocity defines the desired body +Z (backward) axis, so main -Z opposes velocity. Projected/transported prior up defines roll, with a deterministic perpendicular-world-axis fallback for a degenerate initial projection. The existing shortest-arc bounded quaternion PD drives the target. The velocity and selected reference are reevaluated while active. Below 0.5 m/s, manual rotation, pilot cancellation or station exit terminates the maneuver. Completion needs <0.5° and <0.5°/s for 0.5 seconds. It then retains the captured attitude target and reports no automatic burn. Later target/reference changes do not silently restart it. Reset clears advanced policy states.

Bindings remain Input Map actions at the adapter boundary. Runtime controller profiles bind `pad_drift_cancel`, optional `pad_drift_modifier` and `pad_retrograde`; input actions are released before rebinding to prevent stale held state. Start/Guide are reserved. A held modifier and active advanced bindings consume conflicting gameplay operations (including roll, orbit and existing brake buttons), preserving deliberate command priority. A pause-menu camera switch and station-exit route keep controller-only access when A/Y are rebound. Profile selection remains scoped to the existing single local operator; future multiplayer must replace the globally merged action source with per-operator snapshots. No new station or networking system was added.

`ShipTelemetry` now includes local cross-drift, command-active flag, drift ETA, retrograde phase and actual signed force capacities. Automatic force telemetry uses the allocator's actual automatic output, rather than subtracting an assumed symmetric manual rating. Instruments remain observers and never estimate control forces themselves. The computer screen distinguishes rate/hold/retrograde rotation and commanded translation modes; prop bars use signed capacity normalization. F3 retains the expanded technical state without restoring a permanent text overlay.
